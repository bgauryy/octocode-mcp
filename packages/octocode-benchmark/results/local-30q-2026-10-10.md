# Octocode local tools vs a lean shell — 2026-10-10 (30 × 1, corpus-local)

## Verdict

**Octocode v9 is the most correct arm, about as fast as a lean shell agent, and 19% heavier
in characters. It is 2.3× leaner than the published 19.1.0.**

- **Correctness:** v9 scored 10.0, the shell 9.6 (more correct on 8 questions vs 0, same on
  22; sign test p = 0.01). Every shell loss is a precision miss. `sed -n` output has no line
  numbers, so the shell agent miscounted lines on Q26–Q28 and left enclosing functions out on
  Q7. Octocode returns numbered lines and `enclosing` symbols.
- **Characters:** the shell used **0.81× Octocode's characters** (per-question geometric mean,
  95% CI 0.68–0.96; leaner on 21 of 30). The gap sits in basic lookups (0.70×) and edge cases
  (0.53×). On advanced (0.99×) and workflow (1.04×) questions they are level.
- **Time:** tied (shell ÷ v9 = 1.01×, CI 0.93–1.09; both have a 7 s median).
- **v9 vs 19.1.0:** 19.1.0 used **2.32× v9's characters** (CI 2.01–2.69; leaner on only 1 of
  30) and took 1.67× as long. v9 was more correct on 7 questions vs 1 (p = 0.07).
- **clasify:** the arm that offered clasify made **0 clasify calls in 30 runs**, including
  the 7 "described" questions. The agent named the symbols from memory of these well-known
  repos and grepped for them. So `local-mcp-clasify-v9` is a second v9 run: it measures the
  noise floor (9.73 vs 9.93, p = 0.18; characters 0.96×, CI 0.84–1.08).

What decides the remaining character gap, in order of size:

1. **One-call shell idioms with no Octocode equivalent.** Examples are the first line of
   every file (`rg -m1`, Q16: 128 characters vs 6.3k over 4 calls) and a file's line count
   (Q17). See section 5, items 1 and 3.
2. **Structured files have no key path.** JSON and TOML hits don't say which section they
   belong to, so the agent spends a second call (Q12, Q13, Q24).
3. **AST-shaped questions miss the AST rule path.** Q9 cost 20k. A single `astSearch` rule
   answers it in about 2k (checked live).
4. **Per-row noise:** `binarySkipped` warnings and leads on definitional searches, and
   `enclosing` repeated or wrong (C macros).

**Where each side won and why:**

- **v9 over the shell** won on precision:
  - Q26–Q28: the shell cited lines off by one after unnumbered `sed -n` windows.
  - Q7: enclosing functions came free on each hit.
  - Q21: v9 read the non-ASCII file and confirmed its exact contents.
  - Q9: the shell spent 31.9k over 8 calls.
- **The shell over v9** won on characters at equal correctness:
  - one-call idioms: `rg -m1` (Q16), `wc -l` (Q17);
  - plain `rg -n` on small files, where Octocode's JSON envelope (`{"results":[{"index":0,"data":{"files":[…]}}],"root":…}`) is the difference: Q4 662 vs 1,286, Q6 1,503 vs 2,585.
- **19.1.0** lost on characters everywhere except Q12 (a depth tie-break) and Q14/Q17 (fewer calls).
  - Q18: 7/10, it cited `pyproject.toml` line 30 for a line-28 entry.
  - Q7 and Q8: 8/10, wrong or missing enclosing functions.

## What the tools got wrong (fix next)

Each item names the tool, the field, the question and the evidence (call → response excerpt).
"Live" means it was re-run against this tree's MCP after the campaign.

1. **`localSearch` has no per-file match cap: no `rg -m1` equivalent.**
   - Q16 asks for the first line of each of 18 files.
   - The shell did it in one 128-character call: `rg -m1 -n --max-depth 1 -g '*.cs' '' …/Converters/ | grep -v ':1:#region License$'`.
   - v9 needed `structureSearch` + 2 `localSearch` (`resultView:"files"`, then `paginated`) + `localFetch` = 6,261 characters. 19.1.0 needed 10,903.
   - Fix: a `maxMatchesPerFile` (or `firstMatchOnly`) field on `localSearch`.
2. **JSON and TOML hits carry no key path locally** (`localSearch.matches[]`, `localFetch` matchString windows). GitHub reads gained `matchKeys` in v4; local reads did not.
   - Q24: `localSearch matchString:"\"typescript\""` on `nextjs/package.json` returned `{"line":63,"value":"    \"typescript\": \"tsc --noEmit\","},{"line":289,"value":"    \"typescript\": \"6.0.2\","}`. Line 63 is `scripts.typescript`, but nothing says so. The agent spent a second call grepping section headers.
   - Q12: the judge gave v9 depth 4 for "relying on header-order inference" and handed the tie to 19.1.0's whole-file read.
   - Q13: `localSearch backtrace` on `tokio/Cargo.toml` returned lines 90/119/122 without their `[target.'cfg(…)'.dependencies]` table headers, so the agent added a `localFetch ranges:["112-123"]` (876 characters).
   - Live: `localFetch matchString:"\"typescript\"" contextLines:0` gives the same unlabeled lines.
   - Fix: `matchKeys` (`"63":"scripts.typescript","289":"devDependencies.typescript"`) for JSON, TOML table headers, and YAML, on both tools.
3. **The `enclosing` symbol is off by one for C `#define`.**
   - Q4: `localSearch matchString:"define OBJ_ENCODING_LISTPACK\\b"` → `{"line":87,"value":"#define OBJ_ENCODING_LISTPACK 11 …","enclosing":{"symbolName":"OBJ_ENCODING_STREAM","kind":"macro","line":86,"endLine":87}}`.
   - Live on `object.h`: every macro hit is attributed to the macro on the line before (82 → `OBJ_ENCODING_ZIPLIST`, 85 → `OBJ_ENCODING_EMBSTR`).
   - Likely cause: tree-sitter's `preproc_def` node ends at column 0 of the next row, and that end row is used as an inclusive `endLine`. Clamp the end row when the column is 0.
4. **`astSearch` rule queries are the lean path for AST-shaped questions, but agents don't find them.**
   - Q9 (async fns that don't call `asyncify`): v9 spent 20,107 characters on `astSearch operation:"symbols"` (4,412: no `async` flag, no calls) and then a 6-way alternation `localSearch` (7,411).
   - Live, one call returns exactly the 4 free functions plus the methods, about 2k: `astSearch {operation:"match", rule:{rule:{pattern:"pub async fn $N($$$A) -> $R { $$$B }", not:{has:{stopBy:"end", pattern:"asyncify($$$X)"}}}}}`.
   - Gaps:
     - the description names `rule` but gives no `has`/`not` example;
     - the `symbols` view mixes string rows and object rows (`"aprefetch_related_objects (2843-2847, function, exported)"` next to `{"symbolName":"get_prefetcher",…,"members":[…]}`, Q11);
     - `symbols` doesn't mark `async`, so Q11 needed a second regex call (`^(class |def |async def )`) to find the async function.
5. **No cheap line count for one file.**
   - Q17: `localSearch matchString:"\\n" resultView:"countLines" regex:"rust"` → `error: the literal "\n" is not allowed in a regex … hints: - Broaden matchString, path, or filters.` The hint is wrong: nothing needs broadening.
   - The agent then used `matchString:"^"` with `countLines` (146,620, correct). The shell used `wc -l` (150 characters).
   - Fix:
     - the error should say how to count lines (`localFetch` `totalLines`, or `^` with `countLines`);
     - `structureSearch` could show line counts. It currently shows unlabeled byte sizes, `"appendable.go (1838)"` (Q3), which an agent can't tell from lines.
6. **`ranges` input errors don't teach the format.**
   - Q28: `localFetch ranges:"[&quot;299-342&quot;, &quot;440-466&quot;]"` (HTML-escaped by the agent) → `queries.0.ranges.0: "[&quot;…" does not match ^[1-9]\d*-[1-9]\d*$`.
   - Q9 (clasify arm): `ranges:"[{\"s\":\"12-47\"}]"` → `queries.0.ranges.0: Expected string`.
   - A stringified JSON array is already coerced (Q13, Q14 worked with `"[\"112-123\"]"`). Decode `&quot;` the same way, and say `ranges is an array of "start-end" strings` in the error.
   - Same defect as GitHub Q21 on 2026-10-09.
7. **Leads and warnings on successful definitional searches.**
   - 10 `hints.binarySkipped` leads on v9 rows. Each points `structureSearch` at the binaries, which no question needed.
   - Repeated warnings, e.g. Q4 `"binarySkipped: 13 binary files not searched (.rdb 9, …)"` and `"Default excludes skipped 1 dir (build/)…"` (about 370 of Q4's 687 characters).
   - Across the v9 arms, warnings plus hints were 6.9k of 190.8k read (3.6%), concentrated on the smallest calls.
   - Fix: keep the skipped-scope facts, but drop the `binarySkipped` lead unless asked (`extras:["hints"]`), and drop binary counts when the query is a declaration literal.
8. **`enclosing` is omitted on repeated hits in the same parent, and absence reads as "none".**
   - Q7 (clasify arm): 137 had `"enclosing":{"symbolName":"actionBindText",…}`, while 139 and 163 had no `enclosing`. The answer said "Match lines 139 and 163 … showed no enclosing symbol. I attributed them … by line range only."
   - The "named for the first 20 files only" and "over 1 MiB" warnings say `1 hit rows` (grammar). The 1 MiB one also fires on `uv.lock` (Q18), which has no declarations.
   - Fix: on repeated hits, a back-reference (`"enclosing":"↑"`) or a per-file enclosing table; no 1 MiB warning for formats without symbols.
9. **`lspSearch` was never used** (0 of 60 v9 runs), and it would not have helped for half the caller questions.
   - The description lists servers for ts/js, py, rust and c/c++ only. Q8 and Q23 are Go, Q14 is Java.
   - Live `callers` on TS (Q7) is correct except for `actionBoundText.tsx`, reported as `{"symbolName":"actionBoundText.tsx","kind":"module",…,"sites":[137,139,163]}`. Those calls sit in `actionBindText`'s object-literal arrow functions, and `localSearch` already names `actionBindText`.
   - Live `callers` on C (Q15) is correct, but `isPartial` (`noCompileDatabase`).
   - `localSearch` + `enclosing` answered every caller question at 10/10, so this is a coverage note, not a loss.
10. **clasify is never chosen on "described" questions about famous repositories.**
    - Q23 and Q25–Q30 describe behavior instead of naming it, but Sonnet knows tokio, Django, Redis, Guava and Kubernetes. It grepped for the real names (`fn steal_work|MAX_LIFO_POLLS|…`, Q27; `XX and NX|GT, LT|INCR option supports`, Q26) and scored 10.
    - The arm's tool list did include `mcp__octocode__clasify` (checked in each transcript's init event), so this is model choice, not a hidden tool.
    - Measuring clasify needs code the model hasn't memorized (private or renamed sources) or described targets with no greppable literal.
11. **Per-turn context cost.** At the same characters, v9 used 1.88M input tokens to the shell's 1.30M (+45%; cost $2.09 vs $1.89). The cause is the 13-tool list and instructions on every turn, including the 6 GitHub tools and `artifactSearch`, which local work never uses. A local-only tool profile, or trimming the published schema further, closes most of it.

**Agent-side errors** (not tool defects):
- miscounts the tool output got right: "seven" for 8 classes (Q14), "(13)" for 12 files (Q3), "found 9" for 8 calls (Q7), all in the clasify arm;
- an unsupported "probably compiled" inference (Q22).

**What worked** (keep):
- **Numbered content on every read.** It is why v9 never mis-cited a line.
- **`enclosing` on hits:** one call answered caller questions with the enclosing functions (Q7, Q8, Q15, Q23).
- **BOM-aware matching:** Q16's `^#region License$` matched all 17 BOM files.
- **The 8 MB file** returned 3 exact hits (Q17).
- **Non-ASCII paths** listed and read correctly (`⊗.txt (19)`, Q21).
- **Batching three `package.json` files in one call** (Q24).

## Caveats

- **One pass.** The clasify arm is effectively a second v9 pass. Its spread (±1 on 9
  questions, characters 0.84–1.08×) is the run-to-run noise, so treat single-question
  differences of ±1 as noise.
- **Famous repositories.** The model's memory of these codebases shortcuts discovery for
  every arm. It flatters the shell most, because it can grep remembered names, and it hides
  clasify.
- **The judge sees the answer key**, with an instruction to re-verify it on the clone. Its
  verdicts cite `rg`/`sed` evidence, but a shared key error would pass unnoticed. I verified
  each key with the commands it lists.
- **The shell brief teaches lean idioms** (`-m`, `-c`, `sed -n`) the way `gh-lean.md` does.
  The MCP arms get only the server's own instructions, as in the GitHub campaigns.
