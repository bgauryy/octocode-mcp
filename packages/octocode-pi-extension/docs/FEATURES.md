# Feature reference

Detailed behavior of every Octocode for Pi feature. Start with the [README](../README.md) for an overview; configuration lives in [CONFIGURATION.md](CONFIGURATION.md) and the external API in [API.md](API.md).

## File tool

One `file` tool replaces Pi's `edit` / `write`: batched edit / write / delete queries, each with a reasoning line, running on Pi's own engines (exact-match edits, diffs). At session start `file` replaces `edit` / `write` once, unless `--tools` or the `defaultTools` setting names them. A change to a file that moved on disk since the agent read it with `read` (or last changed it with `file`) is refused until it is read again, and so is a change to a file whose read left the context (a rewind, compaction or `/tree` move): size, mtime, ctime and inode are compared, and when the content the agent saw is known (a whole-file `read`, or the tool's own last write) its SHA-256 too. Reads through MCP tools are not tracked: the extension does not depend on any server's tool shapes. A change to an existing file the agent never read this session is refused too (new files are fine). A path outside the repository root (the realpath'd git root) is a `file.outside` [permission](#permissions) ask; anything under the Octocode home (`~/.octocode`, including `pi-trust.json`) is always refused, in every mode. Writes are atomic (sibling temp file, fsync, rename, directory fsync), keep the file's mode, write through symlinks, and fail if the file no longer holds the bytes that were checked.

## Bash

Replaces Pi's `bash` (honoring Pi's `shellPath` and `shellCommandPrefix` settings, foreground and background) with the same streaming output and live `Elapsed` timer, plus a deadline: a waited-for command is stopped after 15 minutes (`OCTOCODE_BASH_TIMEOUT` seconds; the call line shows it, and a `timeout` argument can only shorten it), so a server, watcher or prompt never hangs the turn. `background: true` starts the command as a job in its own process group and returns at once with its id, pid and log file (`<Octocode home>/agent/pi/sessions/<session>/bash/`); the exit status, run time and the last 40 lines arrive later as a message that wakes an idle session. Background jobs have no deadline unless the call gives a `timeout`; at most 8 run at once; job output reaches its log through pipes and only Pi writes it, so a log past 16 MB moves to `<log>.1` (replacing the previous one) and a new log starts with a note naming it, losing or reordering nothing in between; the status bar counts them; `/octocode jobs` lists them with their elapsed time, `/octocode jobs kill <id>` stops one, and all are stopped when the session ends, each reported first without waking the session (a resumed session's brief names any job that never reported, e.g. after a crash). In print, JSON and subagent runs, which end with the agent's run, jobs with a timeout are waited for and jobs without one are stopped at the end of the run; either way their report arrives as one more turn instead of being lost. When output is truncated, Pi's full-output file is moved from the temp dir into the same folder; logs older than 30 days are swept (see [Retention](CONFIGURATION.md#retention)).

## Bash safety

Always on, in every [permission mode](#permissions) and never asked: `bash` and `powershell` calls that would wipe `/` or the home directory (`rm -r` on `/`, `/*`, `~`, `$HOME`, or `--no-preserve-root`), format a disk (`mkfs`), power off (`shutdown`, `reboot`, `halt`, `poweroff`), write to a device with `dd of=/dev/…` erase a disk (`diskutil erase…`/`zeroDisk`, `newfs…`), delete from `/` or home with `find … -delete`/`-exec rm`, or fork-bomb are refused with a reason, even inside `&&`, `;`, pipes and `$(…)`, behind wrappers (`sudo`, `env`, `timeout`, `nice`, `xargs`, `stdbuf`, …), inside `sh|bash|zsh -c` scripts, `eval` and heredoc or herestring bodies fed to a shell. Targets are normalized first (`~/.`, `$HOME/..` and `/usr/..` count as root or home). The parser reads POSIX shell grammar, so PowerShell's own syntax (`Remove-Item -Recurse`) is not recognised. A last-resort guard against accidents, not a sandbox; the environment is passed through unchanged.

## Checkpoints

A turn is one user prompt (typed or sent over RPC); runs woken by team messages or job reports are not turns of their own. Before `file` first changes a path in a turn, its bytes are saved under `<Octocode home>/agent/pi/sessions/<session>/checkpoints/` (content-addressed; files over 8 MiB are skipped with a note; at most 256 entries / 128 MiB per session, oldest turns dropped first; removed with the session's folder, see [Retention](CONFIGURATION.md#retention)). `/octocode rewind [turns]` (default 1) restores the last turns newest first, but only files still exactly as the agent left them; files changed since (by you, bash or a peer) are listed and left alone. `/fork` offers the same restore for the turns after the fork point, and so does `/tree` when navigating away from turns that changed files. Shell writes are not checkpointed.

## Permissions

One permission mode decides which agent actions run and which ask you first. Every ask goes through one helper, in one dialog queue, and is written to the session as an audit entry (`pi.appendEntry`, never sent to the model).

| Action | `manual` | `workspace` | `full` |
| --- | --- | --- | --- |
| Reads in the repository, read-only MCP (Octocode research), `askUser`, `backlog`, `coordinate`, `sendMessage`, project memory | run | run | run |
| Reads outside the repository (`read`, `grep`, `find`, `ls`) | ask | run | run |
| File changes in the repository (`file`, Pi's `edit`/`write`) | ask (the review) | run | run |
| File changes outside the repository, and repository files that run in later sessions (`.git/`, `.husky/`, `.pi/`, `.claude/`, `.codex/`, `.agents/`, `.octocode/hooks.json`, `.octocode/agents/`, `.octocode/skills/`) | ask | ask | run |
| Shell (`bash`, `powershell`) | ask | run | run |
| `web` fetch and search; `browser` navigation (`navigate`, a `tab` that opens a URL) and page actions | ask | run | run |
| `browser` to a private, loopback or metadata host; uploads from outside the workspace | ask | ask | run |
| MCP tools that are not read-only; those annotated `destructiveHint` | ask | run / ask | run |
| Global or pinned memory (save, delete, or moving one out: unpinning, global to project) | ask | ask | run |
| Starting a subagent (`agent`) | ask | run | run |
| A PreToolUse hook's `permissionDecision: "ask"`; a provenance hit | ask | ask | ask |

**Start mode.** Every session starts in `full` (no routine asks), unless you exported `OCTOCODE_PERMISSION=manual|workspace|full`; an invalid value starts in `manual` with one warning. Every session start (new, resume, fork, reload) re-applies that configured start mode and drops the session grants.

**Hard refusals come first** and are never asked, in any mode: the catastrophic shell block ([Bash safety](#bash-safety)), peer reservations ([Team](#team)), elision placeholders copied into a change, writes into the Octocode home by `file` or Pi's `edit`/`write` (shell commands are not parsed for it), shared memory in an untrusted project, `web` to private hosts (unless `OCTOCODE_WEB_ALLOW_PRIVATE=1`), and a PreToolUse hook's deny. A provenance hit and a hook's `ask` appear together in one approval showing both reasons; approving that action also covers its mode ask. A hook's `allow` skips no ask. A destructive MCP hint takes precedence over a contradictory read-only hint.

**Switching.** Shift+Tab in the editor cycles `full` → `workspace` → `manual` → `full` (TUI only); Tab retains its usual completion and selector behavior. This overrides Pi's default thinking shortcut only while the main editor has focus; `/thinking <level>` still sets thinking, and `app.thinking.cycle` can be rebound in Pi's keybindings. Pi's `/hotkeys` shows the configured built-in binding, so the Octocode override is shown in our footer and `/octocode help`. `/octocode permission <mode>` switches anywhere, RPC included. `/octocode permission` shows the mode, what each class does, the session grants and the provenance index size; `/octocode permission grants [clear]` lists or drops the grants; `/octocode permission log` shows the last 50 decisions. A change notifies you and reaches the model as one hidden message (the cached system prompt is unchanged). Changing modes, restarting the session, or clearing grants cancels pending approvals; a late answer cannot authorize a call under the new policy. Choosing a stricter mode clears session grants. Clearing grants or choosing a stricter mode also stops active subagents and pending launches; a saved child conversation can resume after fresh authorization. The footer chip shows the mode and its shortcut: `⏸ permission: manual · Shift+Tab` (accent), `permission: workspace · Shift+Tab` (muted), `⏵⏵ permission: full · Shift+Tab` (error colour); on a narrow terminal it shortens to the mode alone (`⏸ manual`, `workspace`, `⏵⏵ full`) rather than dropping.

**The dialog.** Each ask names the action, exactly what it would do (the whole command, path, URL or arguments, every line of it: nothing runs that was not on screen), and why it asks. The choices are Allow once; Allow *exactly this* for the session; Allow all *&lt;kind&gt;* for this session; Deny; or Deny and tell the agent why. Your note reaches the agent with the refusal. A queued call rechecks newly granted permissions before opening another dialog.

An exact session grant identifies one simple shell command together with its shell tool and working directory, a folder (exactly that folder, not its subfolders), a host, one kind of browser page action, an MCP tool, or a subagent profile with its precise reach. Compound commands have no exact grant. Browser `evaluate`, `attach` and `upload` have no exact grant either. Broad grants such as "Allow all shell commands for this session" are explicit choices. Provenance hits, hook asks and destructive MCP calls never offer or inherit a session grant. *Allow all file changes outside the workspace* also covers repository files that run in later sessions (`.git/`, `.claude/`, …), since both share one kind. `/octocode permission grants` lists grants and `grants clear` drops them; a new session starts without any.

A reply that matches no offered choice decides nothing. Dismissing or interrupting a dialog, including its feedback input, cancels the action; it is not a rejection. In `manual`, the `file` review lists each change and its reasoning, then offers Apply all, Allow all file changes in the repository for this session, Review one by one, or Reject all. You can attach feedback to the whole rejected batch or an individual rejected change. Rejected changes fail with "do not retry" and the feedback; accepted changes are applied after the review finishes. Dismissing an unfinished review cancels the entire batch before any changes are applied.

**Without a UI** (print, JSON) **and in subagents** every ask is denied with a message telling the agent not to retry, to report it to its parent (subagent) or to ask the user (or to start Pi with the `OCTOCODE_PERMISSION` value that allows it). A subagent's mode is its parent's current mode, set explicitly in the child (`OCTOCODE_PERMISSION` from the user's environment never reaches it). Every lingering-agent resume repeats the spawn authorization with the current parent mode and grants, preserving the conversation but replacing the old permission snapshot. An isolated subagent's worktree counts as trusted when its parent trusts the repository it came from (`OCTOCODE_TRUST_ROOT`), so a `full` parent's isolated child stays in `full`. The parent's `agent` row, its `Done (…)` line and a background report count the calls the child could not run for lack of approval (`2 denied`). In `manual`, starting a subagent asks once and shows the profile, what its tools reach and the whole task; allowing it hands the child a grant (`OCTOCODE_PERMISSION_GRANTS`) for the workspace classes that profile reaches (file changes in the repository, shell). Every grantable kind you allowed for the session ("Allow all … for this session") goes to the child too, since it cannot ask; everything else is still denied there.

**Provenance tripwire.** Tool output from open-world sources (`web`, `browser`, MCP tools not marked closed-world, network commands such as `curl`) and private reads (outside the repository, secret-looking text) is indexed in memory as hashes only. A consequential call whose arguments repeat a span of that untrusted text (a shell command, a file path, the content of a file that runs or configures later sessions, runs as code (`*.sh` and other scripts, `bin/`, `scripts/`, `Makefile`, `justfile`, `.envrc`, `.github/workflows/`) or lies outside the repository, an MCP write, a memory), or an outbound call (a URL, a network command) carrying private text, asks in every mode, with no session grant, naming the source. Untrusted text written as data into an ordinary workspace file (a report quoting a page) is not an action, so it does not ask; a shell hit's message says to save quoted material with the `file` tool instead, and a headless refusal carries that reason ("Why it asks: …") so a subagent can act on it. Pi's MCP resource reader counts as open-world, and a `web` search query as outbound. Paraphrase, encoding or splitting defeat it: it is a tripwire, not a boundary.

**Known limits.** Spans under about 33 characters are not matched; one result is indexed up to 256 KB and the index holds about 200k hashes, so a very large result can push out older entries, its own beginning included; network commands are a fixed list (`curl`, `wget`, `ssh`, `scp`, `nc`, …), not `git`, `npm`, `python` or `node`. An MCP tool without annotations counts as a plain MCP write (it runs in `workspace`); only `destructiveHint: true` asks each time. MCP's own default calls an unannotated tool destructive, but asking on every call of such a server, with no session grant, would make it unusable. Messages to other sessions (`sendMessage`) are not gated: a peer acts under its own mode.

**Not a sandbox.** Modes, grants and the provenance tripwire decide what Octocode asks about. They do not limit what the OS user can do: a shell command allowed once can do anything that user can. For a real boundary run Pi in a container or VM (Pi's own `docs/security.md`).

## MCP

Runs the bundled [Octocode MCP](https://github.com/bgauryy/octocode) server (local code search, reading, structure and AST search, LSP, GitHub code/PR search and repositories, packages) on the extension's own MCP client and registers every tool it lists; see [MCP](CONFIGURATION.md#mcp). Tools are named `mcp__octocode__<tool>`, and the prompt tells the model to prefer them for searching and researching code, ahead of Pi's generic "use bash for ls, rg, find" rule. Pi's `read` stays available, and bash stays for builds, tests, git and commands. Every tool, local, LSP, GitHub and packages, is declared directly from the first request, with no `tool_search` step. Their results reach the model whole up to 200,000 bytes per text part (a longer one is saved to the session's `output/` folder, with its path in the result; an image over 600,000 base64 characters is saved and resized with Pi; the fitted image includes its original path and dimension mapping, with a path-only fallback if resizing fails) and are sanitized (terminal controls, bidi overrides, invisible characters) before the model or the terminal sees them. The first prompt waits for the connect (up to `OCTOCODE_MCP_WAIT_SECONDS`); a failed start shows one warning and leaves Octocode routing out of the prompt. `/octocode mcp` shows the server's state and `/octocode mcp restart` starts it again; the process closes with the session and follows a change of folder. A server named `octocode` in Pi's `mcp.json` replaces it.

## Prompt

An Octocode section (about 3 KB) in Pi's structured system prompt covers research routing, verification and delegation, followed by the Octocode MCP server's own instructions, whole, once the server has connected (the first prompt waits for it; see [MCP](CONFIGURATION.md#mcp)). Active tool descriptions own their usage instructions. Delegation mechanics (the subagent limit, report delivery, report files) stay in the `agent` tool description; the section keeps only when to delegate. An agent without `file`, `write` or `edit` gets one "investigate and report; do not modify files" rule instead of the rules about changing files. Subagents get guidance for parent steering, teammate information and automatic reports. A result that should outlive the session goes in a doc under `.octocode/<topic>/` named in the subagent's task; its scratch folder is for throwaway hand-offs and is cleared after a week. The section is rebuilt when active tools, profiles or the subagent's collaborate mode change; identical inputs reuse the cached section. Nothing unique to one subagent (its id, its parent's id, its scratch folder) is in the section, so every subagent of one profile has the same system prompt prefix and siblings share the provider's prompt cache; those facts arrive at the end of its task instead.

## Skills

Pi loads skills from `~/.agents/skills`, `~/.pi/agent/skills` and the project's `.agents/skills` / `.pi/skills`; Octocode also picks up `~/.claude/skills` (except claude.ai's synced skills in its `synced/` folder, which need connectors Pi does not have), `~/.codex/skills`, `~/.octocode/skills` (Octocode home) and, in trusted projects (see [Trust](CONFIGURATION.md#trust)), `.claude/skills` (from the working directory up to the repository root) and `<repo root>/.octocode/skills`, in the main session only: subagents skip these extra directories, and `OCTOCODE_EXTRA_SKILLS=0` turns them off everywhere. Pi loads these skills and reports any name conflict. Install Octocode skills with `npx octocode skill install <name>`.

## Subagents

`agent` runs a task in a fresh Pi process and returns its answer. Every call carries a required `goal`: at most 5 words and 40 characters on what the subagent works on (`audit auth token refresh`); a missing, longer or non-text goal is refused with an example before anything starts, never truncated. The subagent gets a name from a closed list of `adjective-creature` pairs (`inky-kraken`; 1,009 pairs of at most 16 characters, avoiding every live agent and the last 128 subagents this session finished; once the list is used up a numeric suffix is added), and the name, the profile as its role, and the goal show in the panel, `coordinate list`, `/agents`, message headers, the call and result rows, background reports and the subagent's own task (`## You`). The live row and the result read `Done (inky-kraken · 4 tool calls · ↑120k (80% cached) ↓3k · ≈$0.12 · 38s · provider/model)`; a child on a model without pricing shows `cost n/a` (or `+ n/a`), learned from the model named in its own replies. The name is the agent's id: the target of `sendMessage` and `coordinate stop`, the worktree ref and the handoff folder. A role still resolves a `sendMessage` target when only one agent has it. Several calls in one turn run in parallel, at most 3 at once (`OCTOCODE_MAX_SUBAGENTS`); calls over the limit are refused with the running names. `collaborate: true` (or `OCTOCODE_SUBAGENT_COLLABORATE=1` as the default) starts a subagent in team mode: its task lists the collaborating siblings already running (later ones find it with `coordinate list`), and its prompt tells it to message teammates directly when its work affects theirs and to ask them instead of redoing their work. Its final report still goes to the parent. `isolate: true` runs the subagent in a private git worktree under `~/.octocode/pi-worktrees/`: when it finishes, its changes are committed to `refs/octocode/pi/<name>` (or `<name>-2`… when that ref is taken; the report names the actual ref, with a `diff --stat`) and the worktree is removed — if saving fails the worktree is kept and the report names its path; `/agents merge <id>` merges that ref with repository hooks disabled, aborting and listing the files on a conflict. It is refused outside a git repository and warns when the main tree has uncommitted changes (the worktree starts from `HEAD`); worktrees left by a crashed Pi process are committed to their ref and removed at the next start (one that cannot be saved is kept, with a warning naming its path). `/agents kill <id>` (a shortcut for `/octocode agents kill <id>`) stops a background or foreground subagent: SIGTERM to its process tree, then SIGKILL after 5 s to whatever is left, including processes that left its group (a Chrome it launched, its background bash jobs); the run settles only once the tree is gone. Session end stops background subagents before the session leaves the team. A watchdog stops a hung child: no output for 10 minutes while its model generates (`OCTOCODE_SUBAGENT_IDLE_MINUTES`; a running tool or the settle after its answer gets 15 more minutes) kills its process tree and fails the run with `no output for …; last activity: …`; `OCTOCODE_SUBAGENT_MAX_MINUTES` adds an optional wall-clock limit. A child that dies on a signal is reported as `killed by SIGTERM` (not `code null`). Results come back without polling: a background subagent's report arrives as a message when it finishes, and the prompts tell the parent not to poll and the subagent not to announce it is done. A report that finishes after its session ended (a reload) is kept owner-only under the session folder (`reports/pending/`) and delivered once, marked `(Arrived after the session restarted)`, at the next start of the same Pi session. A profile's prompt reaches the child as an owner-only file in the session's `output/` folder, so a prompt that happens to name a path is never read as that file. Each subagent gets a handoff folder, `<workspace>/.octocode/tmp/agents/<id>/` (the `tmp` folder carries its own `.gitignore` of `*`; the path is passed as `OCTOCODE_AGENT_SCRATCH`, with the name's role and goal as `OCTOCODE_AGENT_ROLE` and `OCTOCODE_AGENT_GOAL`; a folder the subagent left empty is removed when it ends, and folders untouched for 7 days are swept at session start). Subagents pick the channel: the report for a short result, `sendMessage` for a blocker or urgent finding, and a Markdown doc in that folder for long or reusable material, reported by path. The parent keeps at most 8 KB / 200 lines of a report in context; a longer one is saved whole as `report.md` there and the kept part ends with its path, so read-only profiles lose nothing. Long reports spill incrementally during execution, so follow-up answers do not accumulate in parent-process memory; retries replace the current report section. A child JSON event over 16 MiB stops the run with an explicit error. Tasks are capped at 16,384 characters. Subagent output is stripped of terminal escape sequences, control characters and bidi overrides before it is drawn. Profiles: `researcher` and `reviewer` (no `file`, `browser` or `askUser`), `implementer` (no `browser`), `webHeadless` and `webLive` (no `file` or `bash`, no MCP: `mcp: false`).

Subagent model routing: coding work runs on Sonnet (`implementer`, `reviewer`: `claude-sonnet-5-5`) and exploration or documentation checks on Haiku (`researcher`, `webHeadless`, `webLive`: `claude-haiku-5-5`), set by each profile's `model`. Before spawning, the profile's model is resolved against the parent's available models (a bare id prefers the parent's provider; `provider/id` and a `:thinking` suffix are kept) and passed as `--model provider/id`. If it is not available the subagent runs on the parent's current model (pinned with `--model`, as is a profile without `model`) instead of failing, and the `agent` row (`Done (… · anthropic/claude-opus-5-5 (claude-haiku-5-5 unavailable))`) and the result details record it. The `agent` call's `model` parameter overrides the profile and is strict: when it cannot be resolved the call is refused with the closest available ids. The running row and result show the resolved model. See [Subagent profiles](CONFIGURATION.md#subagent-profiles). Subagents start with `--no-extensions`, this extension, Pi's built-in MCP and tool search for the user's other servers (`-e builtin:mcp -e builtin:tool-search`, both left out for `mcp: false`, which also starts no Octocode server).

Bundled profiles describe their purpose and evidence requirements in the `agent` tool's profile list. Choose from the profiles actually available in the session:

| Profile | Use for | Capability boundaries |
| --- | --- | --- |
| `researcher` | Uncertain facts, root causes and source evidence | Read-only work, including shell and MCP calls; no file or browser tool |
| `reviewer` | Actionable defects and verification gaps in a specified change | Read-only work, including shell and MCP calls; no file or browser tool |
| `implementer` | A scoped code change with checks and an integration handoff | Guarded file changes, shell and configured MCP; no browser tool |
| `webHeadless` | Rendered public pages and authorized browser interactions | Headless browser and static web; no file tool or MCP |
| `webLive` | Visible browser flows and user-assisted authentication | Visible Octocode browser profile and static web; no file tool or MCP |

Every child starts without the parent's conversation. Its task must carry the goal, scope, relevant paths, evidence, accepted decisions and expected result. Children cannot ask the user directly or delegate again. Their memory schema exposes only reads; their backlog schema allows proposals and permitted updates. Profile instructions make researcher and reviewer shell/MCP work read-only; those instructions are not an operating-system sandbox. The parent owns user communication, missing approvals, review and integration. Questions and replies through `sendMessage` wake idle agents; FYIs wait for their next turn. Completed handoffs arrive automatically, with a saved path for full reports that exceed the context preview.

## Background subagents

`agent` with `background: true` returns at once, so the parent keeps working, talks to the subagent (`sendMessage`, `coordinate list`) and gets its answer later as a message. To redirect one without killing it, the parent sends `sendMessage` with `interrupt: true` (the user `/agents interrupt <id> <text>`): a busy subagent's current step stops (Pi cancels its running tool and model call, or its wait for background work at the end of the run) and the same run continues with that message, marked as an interrupt; an idle one simply wakes. Only the agent that started a subagent, or the user of that session, can interrupt it, and only one subagent at a time; a plain message waits until the running tool returns. If the run cannot be stopped, the interrupt arrives as a plain waking message. The parent can end one it started with `coordinate stop <id>` (the user with `/agents kill <id>`): the subagent's process tree is killed and its report says who stopped it, arriving without waking the parent for another turn and drawn as a stop, not a failure. Every background report starts with the agent's name, role and goal. Reports that finish within 1.5 s of each other arrive together and cost one wake; a report whose `report.md` the parent already read with `read` arrives without one. When a notice (a finished bash job, a team message) wakes a subagent after it answered, its report keeps that answer and adds the later reply after a `---` line. With `OCTOCODE_SUBAGENT_LINGER_SECONDS` set, a finished background subagent stays reachable for that long (its report says so): a message from its parent, or `/agents tell` from you, resumes its saved conversation as a new background run under the same name and goal (taking a slot while it runs), and its reply arrives as another report; `coordinate stop <name>` ends the window early. Nothing runs while it waits. The most recent 128 completed-subagent receipts are kept for this session: `sendMessage` to one says it finished and names its handoff folder. Older ids receive the usual unknown-agent response. In print/JSON runs the process stays open until background subagents finish; interactive sessions are never held.

## Subagent screenshots

Screenshots a subagent takes (`browser`) are saved owner-only under `~/.octocode/pi-team/shots/` (newest 30 kept; files older than `OCTOCODE_CLEANUP_DAYS` are swept). The `agent` tool row draws the latest one live and shows its path; the report ends with `(Last screenshot: path)`. They never enter the parent's context unless it reads the file.

## Agents UI

While this session has live subagents, a panel under the input lists them as a tree (a subagent's own subagents indented under it, working ones first among siblings) with aligned columns: status glyph (teal `●` working, dim `○` idle), name, role, goal, model, state, elapsed time, tools, tokens in the [one token format](#ui) (`↑1.2M (94% cached) ↓35k`), estimated cost (`≈$2.28`; `+ n/a` or `cost n/a` for usage from a model without pricing), flags (`✉ n waiting` for messages not yet answered, `n locks`), then the tool it is running now. A header sums them (`2 working · 1 idle · ≈$0.04`, with `+ n/a` when any agent's usage is unpriced); at most 6 rows, then `+n more`; recent messages between these agents follow. On narrow terminals the tokens drop out first, then cost, tools, flags, age, model and role, before the name, goal and state do. Other sessions' agents never show, and an agent whose heartbeat stopped for 15 s (killed or hung) leaves the panel at once; the store forgets it when its process is gone. Static text only, so scrolling stays stable.

## Team

Agents in the same repository (the main session, its subagents, other Pi sessions that `join`) share the team tables of the agent database (`OCTOCODE_AGENT_DB`, see [Sessions, backlog and memory](#sessions-backlog-and-memory-usage-and-privacy)), scoped by the git root (symlinks resolved, so one checkout reached through two paths is one team). Activity, tool counts and token usage are written on a 5 s heartbeat, so the panel and `coordinate list` can lag a few seconds behind a running agent; a status or goal change waits for the next 1 s tick. A main session is named from the same list when it joins, with the role `main` and, when it runs `coordinate join`, that call's `note` as its goal (same limits as the `agent` goal); no two live agents in the database share a name. A subagent stops when its parent process is gone (it checks every tick that its parent pid is alive and, when the parent spawned it directly, that it was not reparented, so a reused pid does not keep it running; it leaves the team and exits), so a crashed parent leaves no orphan spending tokens. Entities follow the octocode-agents-communication skill: **agents** (name, role, goal, status, current tool, tokens with their cached part, estimated cost and whether part of it is unpriced, heartbeat; the goal is kept in the `task` column), **messages** (immutable, may `replyRequired`, may answer another via `replyTo`), **deliveries** (delivered when the recipient's model is called with it, completed when answered) and **leases** (file/tree reservations). `coordinate` (`list` / `join` / `leave` / `lock` / `unlock` / `changes` / `stop`) shows each agent as `name · role · status · model · parent`, with its goal, join and last-seen time, its work (`56 tool calls · ↑1.2M (94% cached) ↓35k · ≈$2.28`), unanswered messages and held paths, and reserves files all-or-nothing (a trailing `/` reserves a tree; case/Unicode aliases collide). Leases last 90 s past the owner's heartbeat and are released on leave, so a crashed agent frees its files; a subagent's are released when its run ends, and an idle session stops renewing them after 30 minutes (`OCTOCODE_LEASE_IDLE_MINUTES`). A refusal names the holder, its reason and how long ago it locked; `file`, `edit` and `write` are refused on paths a peer holds, and also when the database cannot be read (fail closed, with SQLite's reason; a process that never joined and has no database is not blocked). An agent whose own reservation lapsed is told once and must lock again before editing. Delivery is two-phase: each tick hands everything new (at most 32 messages, in order; the rest wait for the next tick) to Pi as one message, so a busy agent reads the whole batch at its next step instead of one queued message per turn, and the batch wakes an idle agent when any message in it would. A message is marked delivered only when the recipient's model is called with it in the conversation (Pi's `context` event, which covers steered, prompted and quietly appended messages alike); one Pi refuses is offered again on the next tick, and one still queued, or appended after the recipient's last model call, when it is killed or leaves becomes a dead letter. Heartbeats prune resolved message history older than a day, with pruning checked at most once per minute. Unread messages, questions still awaiting replies and unreported dead letters remain until resolved; they have no separate expiry. Messages a departed agent never read are kept as dead letters (`dead-lettered` in the panel); the sender is told once, without a wake (`Message #N to X was not read: X left`), and sending to an agent that already left is refused. A headless subagent takes no message while it is idle and leaves the team when its run settles, so a message that arrives after its last turn is dead-lettered instead of falsely acknowledged. `coordinate changes` lists the files agents changed recently with `file`, `edit` or `write` (successful changes only; a partly failed `file` batch records only its OK queries), newest first, one row per file with the agent, tool, age and change count; `paths` narrows it to prefixes, `withinMinutes` (default 60, at most a day) and `limit` (default 20) bound it. Changes are kept a day; changes made by you, bash or git are not tracked, so use `localSearch` (`operation: "files"`, `time.modifiedWithin`, `sort: "modified"`) for what changed on disk. When the database is refused, `/agents` and the status bar show `team off` with the reason (schema 3 added the agents' cached-token and unpriced columns, so an older extension still running in another Pi session sees the database as newer and shows `team off` until it is updated); one that is only busy or locked shows `team retrying` and the panel appears once a read succeeds. After the machine sleeps (a 1 s tick arrives more than 15 s late), the first tick of each session gives the members and reservations that were live before the sleep a fresh heartbeat and lease, so nobody is dropped, and no message dead-lettered, for the time everyone was suspended; an agent that stays silent after the wake is dropped as before. `OCTOCODE_TEAM_WORKSPACE` (absolute path) overrides the git-root scope, so an isolated worktree subagent joins its parent's team. `sendMessage` (to a name, a unique role, `parent` or `all`) is queued (`Queued message #N for …`) and arrives within a second as a message headed `Message #N from agent inky-kraken (reviewer: audit auth token refresh)`, with the sender's role and goal while it is still on the team: a busy agent reads it at its next step; an idle one wakes only for a message that requires a reply, the answer to its own still-open question (`replyTo`), or a message from the user or the API (an FYI, or a reply to a reply, waits for its next turn). An unknown `replyTo` id is refused. `all` reaches the sender's session tree (its top session and every subagent under it), not other sessions in the repository; `/agents tell all` and the API's `agents.tell all` reach the current session's tree. Messages over 8,000 characters are rejected before queueing; send a summary and a file path for larger content. An oversized body written by another process is withheld from model context with an explicit delivery-error notice, rather than injected as a partial instruction. API messages are labelled as from an external, untrusted client; `agents.tell` takes at most 8,000 characters and a refusal is an RPC error. `/agents` (also `/octocode agents`) lists the team (goal, activity and message text stripped of terminal escapes) and `/agents tell <agent\|all> <text>` messages agents as the user (`/agents interrupt <id> <text>` redirects a subagent at once). Reservations are cooperative: they do not cover arbitrary shell writes.

## Sessions

`/sessions` (same as `/octocode sessions`) lists sessions from Pi's `SessionManager` (so sessions from before Octocode was installed too), with what Octocode keeps in the local agent database (`<Octocode home>/agent/pi/octocode.db`): branch, git HEAD, cost, tokens, files changed, and whether its process is running. Octocode does not name sessions. It lists this repository's sessions newest first (`all` for every repository, or words to match name, first prompt, repository, branch or id; each line ends with the tail of the session id, and a fork with no prompt of its own shows `↳` and its parent's first prompt) and offers Resume (Pi's `switchSession` on the session file), Details, Rename (the current session only: Pi owns session names) and Forget Octocode data (deletes the session's Octocode folder and extras row; Pi's session file stays; refused while another Pi process has the session open). Resuming a session (or restarting Pi on one that already has prompts) adds a short brief before the next prompt, read when that prompt is sent, only when there is something to say: the git branch or HEAD moved, this session has ongoing backlog items, or you were away over an hour (the to-do count and uncommitted changes are then added as context, but never cause a brief alone). Its first line carries the away time and the most important change, so the collapsed transcript line shows both. Pi's own `/resume`, `/session` and transcripts are unchanged; `/sessions` is an extra picker. Subagents run with `--no-session`, so they get no session file, extras row, brief or command.

## Backlog

A task board per repository (worktrees share their main repository's) in the agent database, with states `backlog` (triage inbox) → `todo` (accepted) → `ongoing` (claimed) → `done`, priorities `p0`–`p3`, tags and a log of notes and changes. An item may name the item it came from (`from`: a split, follow-up or finding, shown as `(from B12)`); `get` on the origin lists every item that came from it with its state, `list` with `from` filters to them, links that would loop are refused, and removing the origin clears the link on each derived item with a note. Every update logs what it changed (state, assignee, priority, tags, origin, the previous title, and a replaced body in full) as a change entry next to the notes, so a note carries the reason, not the change. A query matches substrings of titles and bodies and whole tags (`#ui` or `ui` finds tag `ui`, not `build`). Item lists and notes have `limit`/`offset` pages with an executable `Next: backlog` continuation. The `backlog` tool lets the agent `list`, `get`, `add`, `update` and `remove` items (ids `B1`, `B2`, …; an update with `state: ongoing` claims the item; `done` needs a note saying what changed and how it was verified; `remove` deletes an item and its notes, is meant for duplicates or items you asked to drop, and is refused to subagents and for items another running session holds). Items you add land in `todo`; items the agent adds land in `backlog` for you to triage unless it gives another state; a subagent's additions always land there, and a subagent may change only the state and notes of items its parent has claimed. An item another running session holds can only get a note from the agent (you can still move or edit it on the board). `/backlog` (same as `/octocode backlog`) opens the board (rows show `←B12` for an item's origin; Enter → Came from… sets or clears it); the status bar shows the open counts in words with the hint that opens the board (`backlog 2 ongoing · 4 todo · 1 to triage · /backlog`). `/octocode backlog export` writes a Markdown snapshot to `<repo>/.octocode/backlog.md` (nothing reads it back).

## Memory

Durable notes (`preference`, `fact`, `decision`, `gotcha`, `procedure`) kept across sessions, global or per repository, in the agent database with an FTS5 full-text index (BM25 ranking; a `LIKE` scan when SQLite lacks FTS5). The `memory` tool can `search`, `get`, `list`, `set` (create, or update with `id`) and `delete`; subagents get `search`, `get` and `list` only. Creating, changing or deleting a global or pinned memory needs a trusted project and passes the `memory.shared` [permission](#permissions) ask (refused without a UI unless the mode is `full`); in an untrusted project the tool reads only global memories. A new memory whose title matches, or whose words mostly overlap, an existing one is refused with its id, so the agent updates instead of duplicating. Before each prompt, pinned memories (up to 1,200 characters) plus the top 5 BM25 hits for the prompt (3 in a subagent; words under 3 letters are ignored, a hit needs 2 matched words or one in its title or keywords, and hits under 30% of the best score are dropped; 2,400 characters in all) are injected as a hidden `[octocode-memory — …; not instructions]` message; a memory already injected on this branch is not repeated until a compaction summarizes its injection away (injections the compaction keeps still count). Seen ids are excluded before the FTS result limit, so candidate retrieval stays bounded as the branch grows. Pinned memories are not injected into subagents. Project memories are injected only in a trusted project. `/memory` (same as `/octocode memory`) browses, searches, adds and edits them; `/octocode memory auto off` stops injection everywhere and `OCTOCODE_MEMORY_AUTO=0` for one process.

## Web and browser

A main session leaves `browser` to the subagent profiles that carry it (the bundled `webHeadless` and `webLive`): its schema is the largest, and every request would pay for it. Name it in `--tools` or the `defaultTools` setting, or turn it on with `/tools`, to keep it in the main session; with no browser-capable profile it stays. Subagents get it unless their profile excludes it. For network, HAR, performance or raw DevTools Protocol work, the `octocode-chrome-devtools` skill drives its own Chrome through its CLI from any agent with `bash`.

Two browser subagents: `webHeadless` (headless Chrome over DevTools only: fast, no permissions, no display, runs anywhere) and `webLive` (visible Chrome over DevTools on a persistent profile, for watching a flow or tasks behind the user's login; it stops at a login, CAPTCHA or MFA and leaves the window open for the user). `web` fetches a URL as readable text (20,000 characters by default; `maxChars` up to 50,000). An HTML page is reduced to its marked main content (`<main>`, `role="main"`, or a single `<article>`) when it has one; a longer page is saved whole under the session's `output/` folder (see [Where files go](CONFIGURATION.md#where-files-go)) and the inline part folds runs of 8+ link-only lines (sidebars, tables of contents) and names the file to read the rest from, so nothing is refetched. Fetched HTML is static (no JavaScript runs): hidden elements are dropped, page metadata (JSON-LD, Open Graph prices, locale and dates) comes first, and the result notes a JavaScript app or an empty shell, whose rendered values (prices, currency) may differ, so the model confirms them in `browser`. The body is decoded in its charset (a byte-order mark, the `Content-Type` charset, else an HTML `<meta charset>`, else UTF-8). Transient failures (network errors, 408/425/429/5xx, a short `Retry-After`) are retried twice with backoff and a final failure names its cause (`ECONNRESET`, `ENOTFOUND`, …); pages are cached for 15 minutes (at most 64 pages and 32 MB, least recently used first), and parallel fetches of one page share one request; a redirect to another host is reported, not followed. `web` also searches the web (Tavily / Serper / Exa / Brave with an API key; without one DuckDuckGo, then Bing, then DuckDuckGo lite, with the skipped providers and why named in the result). It refuses loopback, private, link-local (cloud metadata), CGNAT, multicast and reserved addresses, checking the resolved host and every redirect hop, and connecting only to the addresses it checked, so DNS rebinding cannot redirect the request (`OCTOCODE_WEB_ALLOW_PRIVATE=1` turns the address check off; only `http(s)` is ever fetched). `browser` is the in-process CDP tool for both. It opens only `http(s)` URLs; a private, loopback, link-local or cloud-metadata host, or a name that does not resolve (Chrome's own DNS may still take it somewhere private), is a `net.private` [permission](#permissions) ask, allowed per host for the session (or always, with `OCTOCODE_WEB_ALLOW_PRIVATE=1`). The check covers every page and frame load the driven page makes (redirects, link clicks, script navigations; a refused load fails and the result names it), and a tab the page opens on its own is checked once loaded. Only document loads are checked: a public page's own XHR, fetch and image requests to a private host are not (the page can read their answers only when that host allows CORS). `upload` of files outside the workspace, symlinks resolved, is an `upload.outside` ask. It never connects to a running Chrome on its own: `attach(port)` drives an already open DevTools browser in place, and `OCTOCODE_CHROME_PORT` opts in to working in a tab of the Chrome on that port (a headless Chrome is launched when nothing listens). Deep checks can reuse the reported port with the `octocode-chrome-devtools` skill's scripts. Actions: navigate (after the load event it waits until content and requests are quiet for 500 ms, at most 6 s, and notes a page still changing; with `text` it also waits for that text), snapshot (with `text`, waits for it first; a `Locale:` line names the page language, browser language, time zone and the currency symbols on the page; footer links are listed compactly on one line) (capped at 8 KB: numbered elements first, with each field's value and state, then page text; a cut snapshot is saved whole to a file; page text past 200,000 characters is not read, and the `## Text` heading then says how much the page held), click (a real mouse press at the element's centre, so mousedown/pointer handlers run; it reports an element covering the target), hover (a bare mouse move, for hover menus and tooltips), drag (`ref` onto `to`, or onto the smallest element showing `text`: an HTML5 drag is intercepted and finished with dragEnter/dragOver/drop, a pointer drag gets paced moves and a release), type (replaces a text field's or contenteditable's text, picks a `<select>` option by label, and is refused when focus does not land on a text field), fill (several fields in one call; checkboxes, radios and switches take `true`/`false` and are clicked only when they differ; failed fields are listed), press (a key or a combo such as `Control+A`, `Shift+Tab`; editing shortcuts are sent as Chrome commands so select-all works), wait (until `text` appears, or with `gone` disappears, up to `timeout` seconds, default 10, max 60; a timeout fails with the current page attached), tabs and tab (list tabs with stable numbers; switch by `index` or open `url` in a new one), evaluate, screenshot (visible page, jpeg quality 70 unless `format: "png"`; the full-size file is saved under the session's `output/` folder and its path is in the result; an image over 600,000 base64 characters is retaken at 0.5× then 0.25× and, if still too large, only the path is returned, so screenshots cannot exhaust the request size limit), console (each message clipped to 2 KB, the last 200 kept), `dialog` (answer an open alert/confirm/prompt; while one is open, snapshot reports it instead of blocking), `upload` (sets files on a file input, or on the chooser a click opens), `download` (optionally clicks, waits, and lists each saved file with its path in the session's private `output/downloads/` folder); aborting the tool call cancels its pending page calls, and a Chrome still starting for it is killed once it is up. Elements come from open shadow roots and same-origin frames too (cross-origin frames are counted, not shown), and include `draggable` elements and the outermost `cursor: pointer` elements holding no other control (framework click handlers leave no attribute). An element keeps its number while it stays in the page (new ones get new numbers; a new document starts at 1), so numbers from earlier results stay valid. Mouse actions move first and measure the element again, since a move can shift the layout (a hover menu closing). After an action the tool waits about 150 ms for a navigation, for its load if one started, then until the DOM is quiet for 150 ms (at most 3 s); a tab the action opened (`window.open`, a popup) becomes the driven tab. On the same page, actions return only the new or changed elements, the numbers no longer shown, and new text lines, instead of a full snapshot. A headless Chrome gets a 1366×900 window, so sites keep their desktop layout. A headless Chrome that `browser` launches gets a fresh profile under `<Octocode home>/pi-browser/`, removed when it closes (and swept at the next launch if the Pi process died). In `webLive` the Chrome is visible and uses the persistent profile `<Octocode home>/pi-browser-profile/`, so a login survives between runs; the window stays open when the subagent ends (`browser close` quits it), and the next `webLive` reuses it through the profile's `DevToolsActivePort` file, once the Chrome on that port proves to be the one that wrote it (its DevTools browser id matches; a stale file is removed). A Chrome open on that profile without DevTools is refused with a clear error.

## askUser

Ask for missing user decisions or facts (1–4 related questions per call). Choices, descriptions and short tab labels are optional; a question without choices opens a text editor directly. The inline dialog shows progress, retains typed drafts, and reviews answers before submitting a batch. Single-choice questions answer on Enter; multi-select questions toggle choices with Space or Enter and answer only from their **Submit selection** row (at least one choice or a written answer). RPC hosts use numbered choices and text inputs. Cancellation, interruption and an unavailable user are distinct; unanswered questions never supply approval. Continue independent work within existing authorization when a required decision is missing.

## Hooks (opt-in)

With `OCTOCODE_HOOKS=1`, Claude Code / Codex command hooks run on Pi events: `PreToolUse` (exit 2 or a `block`/`deny` decision blocks the tool; `permissionDecision: "ask"` asks you in every [permission mode](#permissions), and is denied without a UI; `allow` skips no ask), `PostToolUse` (feedback and `additionalContext` are appended to the result), `SessionStart` (runs in the background so startup is not held up; its output is added to the next prompt's context, which waits for it), `PreCompact`, `Stop` (when a run completes; exit 2 or `{"decision":"block","reason":…}` continues it with the reason as `Stop hook feedback`, with `stop_hook_active` and `last_assistant_message` as in Claude Code, and at most 8 continuations in a row until a tool runs; `continue: false` is not a block) and `Notification` (in the background, never blocking: `permission_prompt` for a confirm dialog, `elicitation_dialog` for other dialogs, `idle_prompt` after an answer sat unread for a minute; the matcher is the type). All matching hooks run in parallel, and one listed in several files runs once. Pi checks every call of a batch before any runs, so a slow `PreToolUse` hook holds the whole batch: the working line shows `Checking bash …` while it runs, the row shows `checks 1.2s` afterwards, a hook over 5 s is reported once, and `/hooks` lists runs, average and slowest time per command. Read from `~/.claude/settings.json`, `~/.codex/hooks.json`, `~/.octocode/hooks.json` and, in trusted projects only (see [Trust](CONFIGURATION.md#trust)), `<repo root>/.claude/settings.json`, `.claude/settings.local.json`, `.codex/hooks.json` and `.octocode/hooks.json`. Matchers accept Pi or Claude tool names (`Bash`, `Edit\|Write`); the payload is Claude-shaped: `bash` is `Bash` (same `command` input), `read` is `Read` with `tool_input.file_path`, and each `file` query is its own `Edit`, `MultiEdit`, `Write` or `Delete` call with `tool_input.file_path`; other tools keep their Pi name, and `pi_tool_name` is always the Pi name; hook text added to the context is capped at 16 KB.

## Context, cache and cost

Old, large tool results, the arguments of old successful calls and old images are trimmed when that pays for the prompt-cache rewrite or the cache is cold anyway; every removed piece is saved first and the note names the file, its SHA-256 prefix and size. Interactive sessions use 1-hour cache retention, headless runs and subagents 5 minutes (an exported `PI_CACHE_RETENTION` wins); custom Anthropic models get cache lifetimes in Pi's registry so Pi's warmer runs for them. Summaries are Pi's own. Costs are Pi's list-price estimates, shown as `≈$` (`n/a` for unpriced models) next to `↑ prompt (cached %) ↓ output`. The full design, formulas, measurements, subagent behaviour and known limits: [CONTEXT-AND-COST.md](CONTEXT-AND-COST.md).

## UI

In the TUI Octocode draws the header as the "OCTOCODE CODE" banner: a 6-row block font (2-row half-block font, then plain text on narrow terminals) painted along the theme's accent → link → operator gradient with box-drawing shadows, a tagline with the version, and key hints. It has a fixed height, writes nothing to the session (so `/new`, `/resume` and `/fork` keep it in place), and a light band sweeps across it once per process. The footer has two lines: model, the [permission mode](#permissions) chip (kept, in its short form, on narrow terminals), thinking level, a context bar coloured by fullness, running agents and bash jobs, `tok/s` and cost; then cwd, branch, session name, tokens and other extensions' statuses (Pi's MCP, hooks, backlog), dropping the least important parts on narrow terminals. Tokens and money have one format everywhere (footer, agents panel, `coordinate list`, `/agents`, subagent rows and reports, `/sessions`). Tokens read `↑1.2M (94% cached) ↓35k`: ↑ counts every prompt token (uncached input plus cache reads and writes), the share is cache reads over that total, shown when there are any. Money reads `≈$2.28`: Octocode never prices tokens itself; it sums Pi's per-reply cost, computed from the model's `cost` rates in `models.json` at list price (no gateway discount, regional surcharge, fast or batch modifiers), so it is an estimate. A model with no `cost` there gets all-zero rates from Pi; its usage is not silently counted as free: the cost shows `≈$2.28 + n/a` when part of the usage is priced and `cost n/a` when none is, and the first such reply in a session warns once (`<provider>/<model> has no pricing in models.json; its usage is not in the cost`). Free local models are marked the same way; add `cost` rates to `models.json` to price a model. The spinner cycles braille dots along the same gradient; hidden thinking shows `✻ Thinking… (ctrl+t)`; the terminal title is `octocode · <session name> · <dir>`. Octocode also adds a generation-speed (`tok/s`) status and one `/octocode` command (see [Commands](../README.md#commands)). The working indicator names what the agent is doing now: `Thinking`, `Writing`, `Preparing tool calls`, `Running bash yarn test`, `Running 3 tools: bash · localSearch ×2` (every top-level call of a parallel batch; calls a tool makes itself are part of it) `Checking bash …` while a call's `tool_call` checks (reservations, the shell guard, PreToolUse hooks, permission asks) run, or `Waiting for you: <title>` during a dialog (`(+N queued)` when more wait), with the elapsed time once a step passes 2 s; Pi's default comes back when the run ends. The same line, without the time, is the agent's activity in the agents panel. Messages Octocode queues while the agent works (subagent reports, background bash reports, teammate messages) show as `✉ n queued` until the agent reads them. Pi's Esc clears its whole queue but restores only your typed text; Octocode adds the queued messages it cleared to the conversation without starting a turn and says so (TUI only; RPC keeps Pi's queue for the next run). A tool row whose call waited before it ran adds `checks 1.2s` (its `tool_call` checks) or `queued 2.0s` (other calls' checks or the tool's lock) once the wait passes 250 ms.

**One dialog at a time.** Pi's TUI draws one dialog; a second one replaces the first, whose answer then never comes. Every interaction that asks (`askUser`, every permission ask including the file review, `/octocode` subcommands, leave and checkpoint prompts) holds one shared queue, so a batch with `askUser` and a reviewed `file` asks one after the other. A call aborted while it waits stops waiting at once.

**Answer-ready notifications.** When the agent finishes an answer or opens a dialog while the terminal is in the background, Octocode sends a desktop notification (OSC 9, OSC 777, Kitty's OSC 99, or the bell; see `OCTOCODE_NOTIFY` and `OCTOCODE_NOTIFY_METHOD` in [CONFIGURATION](CONFIGURATION.md)) and puts `●` in the terminal title until you are back. Focus comes from terminal focus reports, which Octocode turns on in the regular TUI; in fullscreen mode Pi keeps them to itself, so Octocode notifies only after runs of 30 s or more with no key pressed for 30 s. Aborted runs, subagents and print, JSON and RPC modes never notify.

Tools batched in one assistant message run in parallel. `file`, `browser`, `memory` and `backlog` keep their own calls in order with a per-tool lock, and `askUser` waits in the one dialog queue every interaction shares, instead of Pi's `executionMode: 'sequential'`, which would make every other call in the batch (MCP searches, bash) wait too. Put dependent steps, such as an edit and the test that checks it, in separate messages. Every tool renders compactly like Pi's built-ins: a one-line call, a short result preview, full output on ctrl+o. `file` shows each change's reasoning under it, with +/- counts and inline diffs. An `agent` row reads `● Agent(profile · goal)` (the model and `isolated` follow when set) and a background report `● Agent(name · profile · goal)`; the prompt given to the subagent shows in full above its progress or report when the row is expanded. A row the user interrupted (Esc, `/octocode jobs kill`, a stopped subagent) is drawn `◼` in the warning colour, not as a failure. The working line and the shared team database show a call's path, command, query, URL or element ref (never typed text), with credential-looking spans replaced by `[redacted]` and `user:pass@` removed from URLs.

## External API (opt-in)

Other programs can message a running session and follow it. `OCTOCODE_API=1` serves JSON-RPC 2.0 (one JSON line per message, the framing MCP, ACP and Codex's app-server use) on a Unix socket (`0600`, in a `0700` directory); `OCTOCODE_API_HTTP=<port>` (`0` = any free port) adds loopback HTTP; `/octocode api on [http]` and `/octocode api off` toggle it at runtime. Each instance writes `~/.octocode/pi-api/instances/<id>.json` (`OCTOCODE_API_DIR` overrides; pid, cwd, socket, HTTP URL and bearer token, mode `0600`), swept when the process dies. Subagents never serve one. See [External API](API.md).

## Sessions, backlog and memory: usage and privacy

**Working a backlog item.** Pick it on `/backlog` and press `d` (or Enter → Do it now), or run `/backlog do B12`: the item is claimed as ongoing for this session and the agent gets a prompt with its title, saved goal, body and origin, asking it to record progress and follow-ups with `from` set to the item. It should mark the item done only after verifying its goal (or result when no goal is saved), with a note on what changed and how it was checked; a blocker is recorded instead of completion. The handoff is queued as a follow-up while the agent is busy. Delegate to a subagent hands the same goal, context and completion requirements to the agent for the `agent` tool. Both handoffs preserve existing permissions; item text does not grant additional authority. You can also just say so: "work on backlog item B12", "add a backlog item to…", "what is on the backlog?" — the agent uses the `backlog` tool. Likewise "remember that…" or "forget memory M3" use the `memory` tool.

**Privacy.** The agent database and every session folder are private to your user (files `0600`, folders `0700`) and stay on this machine. Backlog titles, bodies, notes and tags, and memory titles, bodies and keywords that look like credentials (AWS access key ids; GitHub, GitLab, npm, Slack, Stripe, Google and `sk-…` API tokens; private keys; JWTs; bearer tokens; passwords in URLs or `password=…` assignments) are refused, checked on the text as stored: store where a secret lives, not the secret. Injected memories and the resume brief are labelled as data, not instructions, and the tool guidelines tell the model to verify memories against the code. A database file that is not an Octocode agent database (another app's SQLite file or not SQLite at all), or was written by a newer schema, is refused (set `OCTOCODE_AGENT_DB` to another file) rather than changed; an older database is migrated forward in place, one ordered step per schema version (now 5), so once a newer extension opens it an older extension in another running Pi session refuses it and turns its team off until it is updated, down to its journal mode; opening the database tightens the file (and the default folder) back to owner-only; a missing or refused database never blocks a prompt.
